# 自动化评估网关与裁判可信度

评估系统本身也是要被评估的。这一层解决两个正交的问题：

1. **吞吐**——评估要跑得完。判官调用是 IO 密集的，串行跑一遍全集要几十分钟，
   而无节制并发会撞限流并以连接错误的形式失败。
2. **可信**——评估的数字要是真的。LLM 裁判会幻觉、会偏见、会对措辞而非事实
   打分，一个失准的裁判会让下游每一个指标都在测别的东西。

---

## 1 限流层

三种机制，各自覆盖另外两者管不到的限制（[`src/eval/rate_limit.py`](../src/eval/rate_limit.py)）：

| 机制 | 挡住什么 | 为什么不能省 |
|---|---|---|
| Semaphore | 并发连接数 | 供应商独立于吞吐限制并发。500 个任务 `asyncio.gather` 会开 500 个 socket，失败形式是连接重置而非 429，退避重试救不回来 |
| RPM 令牌桶 | 每分钟请求数 | — |
| TPM 令牌桶 | 每分钟 token 数 | 判官 prompt 带检索上下文，动辄数千 token，**token 上限远早于请求上限触顶**，是实际的绑定约束 |

两个桶都**连续补充**而非按分钟窗口重置。窗口式限流器允许一次突发在窗口第一秒
把整分钟额度抽干，供应商看到的是尖峰，照样拒。

### 429 退避

即使客户端限流正确，429 仍会发生——额度是这个 key 的所有调用方共享的。

- 优先解析供应商给的等待时间。Groq 把它写在 message body 里
  （`Please try again in 7m31.008s`），供应商知道窗口何时重开，猜是严格更差的。
- 没有提示时用 **full jitter** 指数退避：`sleep = random(0, base × 2^attempt)`。
  固定退避会让整个队列锁步重试，第二波 429 比第一波更糟。
- 单次退避上限 60s。CI 被一个明天才重置的额度堵十分钟，它已经失败了，只是还没说。
- **只重试限流与瞬时传输故障**。重试一个 400 只是在烧额度复现 bug。

## 2 异步队列：实测

[`src/eval/async_runner.py`](../src/eval/async_runner.py)，用
`src.eval.queue_bench` 实测。12 次判官调用，`deepseek-v4-flash`，并发 6。

**做了对照平衡**：两轮试验交换串行/并发的先后顺序，因为先跑的一半要付连接建立
和冷缓存的代价，固定顺序的偏差不会自己抵消。

| 试验 | 顺序 | 串行 | 并发 | 加速比 | 单调用延迟漂移 |
|---|---|---|---|---|---|
| 1 | 串行先 | 58.8s | 21.0s | 2.80x | 1.84x |
| 2 | 并发先 | 71.8s | 14.6s | 4.93x | 1.32x |
| **均值** | | | | **3.86x** | |

并发 6 只拿到 3.86x（理想值的 64%）。原因在最后一列：**并发时单调用延迟涨到
1.3–1.8 倍**——供应商在服务端排队，客户端的并发没有全部兑现成吞吐。

> 第一次只跑一轮时测得 6.61x，即"并发 6 拿到 110% 的理想加速"。这不可能，是
> 供应商那一分钟状态较好造成的假象。对照平衡 + 报告延迟漂移就是为了不让这种
> 数字进文档。

## 3 分层门禁

三层，按各自能承担的代价划分：

| 层 | 触发 | 内容 | 阻断 | 理由 |
|---|---|---|---|---|
| **PR** | 每次 push | `ci.yml` 的 `eval-gate`，确定性检索指标，无 LLM，秒级 | ✅ | 判官是随机的，放在这里会让 merge 因与改动无关的原因变红 |
| **Nightly** | 每日 03:00 UTC | 全集过判官，走异步队列 | ❌ | 只报告和看趋势 |
| **Release** | 发版 | 判官与人工的一致性 | ✅ | 判官失准会静默作废它产出的所有数字 |

只有发版层阻断在 LLM 相关的数字上，而且阻断的是判官的**校准度**，不是任何单次
裁决。（[`.github/workflows/eval-tiers.yml`](../.github/workflows/eval-tiers.yml)）

### Batch API

夜间全集走 Batch 端点（[`src/eval/batch_api.py`](../src/eval/batch_api.py)）：
约五折价格、不受每分钟额度约束，代价是延迟从秒级变成小时级——夜间任务有的是
时间，PR 门禁没有。

打包成 JSONL，每行一个请求，带 `custom_id`。这个 id 是结果与用例之间**唯一的
关联**：批量响应乱序且可能缺失，按下标 join 会在任何一个请求失败的瞬间开始
静默错位。所以：

- 重复 `custom_id` 直接报错——否则一个结果会无声覆盖另一个。
- 拆分同时按请求数（5 万）**和字节数**（100 MB）——带上下文的 prompt 会在远未
  触及请求上限时先撑爆文件大小限制，供应商会拒掉整个上传而非溢出的尾部。
- `reconcile()` 单独报告 coverage。用回来的那 80% 算出的基线和昨天的不可比，
  照比会让门禁把覆盖率变化当成质量回归来报警。

## 4 幻觉与偏见抑制：改进前后

### 4.1 用已知真值构造对照

[`src/eval/judge_ab.py`](../src/eval/judge_ab.py) 从真实车库渲染上下文，成对生成：

- **忠实答案**——完全由上下文字段渲染。
- **同一答案 + 一句注入的假话**——两者**共享上下文**，所以两者得分之差只可能
  由注入的那一句造成。

注入分两档难度，这一点是整个实验能不能测出东西的关键：

| 档 | 例子 | 作用 |
|---|---|---|
| blatant | "实测续航可达 1200 公里"、"标配 L4 级全自动驾驶" | 任何读了答案的裁判都能抓到 |
| **subtle** | "整车质保为 3 年或 10 万公里"、"综合工况油耗约 6.8L/100km" | 平淡、合理、和周围的真话读起来一模一样 |

> 第一版只有 blatant 档，测出来 naive 检出 75%、cot 100%、structured 100%——
> **结构化裁判没赢**。原因不是结构化没用，是用例太简单，已经饱和了。换成
> subtle 档后 naive 检出直接掉到 30%，差距才显出来。一个只由显眼错误组成的
> 用例集，测的是用例设计，不是裁判。

### 4.2 三层抑制

1. **CoT rubric**——先说理由再打分。
2. **强制解码路径**（`structured`）——按 `<quotes>` → `<reasoning>` → `<score>`
   的顺序输出，且明确要求 quotes 必须是上下文原文逐字摘抄，找不到就写「无」。
   顺序是强制的：先摘证据再推理再打分，模型无法先拍一个分数再补理由。
3. **证据校验**——`verify_quotes()` 检查摘抄的句子是否真的出现在上下文里。
   解码路径强制它**产出**证据，没有任何东西强制那证据是**真的**；一个自己编一句
   引文再据之打分的裁判，走完了仪式跳过了要点，而且它下游的推理会写得无可挑剔。
4. **原子断言拆解 + NLI**（`atomic`）——把答案拆成独立断言逐条判定蕴含。

### 4.3 结果

subtle 档，12 对用例 × **3 次重复**，`deepseek-v4-flash`：

| 模式 | separation（均值 [范围]） | 幻觉检出率 | 误报率 | Cohen's Kappa |
|---|---|---|---|---|
| naive | 0.444 [0.433, 0.467] | 30% [25%, 33%] | 0% | 0.305 [0.250, 0.333] |
| cot | 0.844 [0.733, 1.000] | 81% [67%, 100%] | 3% | 0.778 [0.667, 1.000] |
| **structured** | **0.856** [0.683, 0.967] | **86%** [67%, 100%] | **0%** | **0.861** [0.667, 1.000] |
| atomic | 0.622 [0.550, 0.683] | 97% [92%, 100%] | 14% | 0.833 [0.750, 0.917] |

- **naive → cot 是唯一稳健且巨大的提升**：检出 30% → 81%，kappa 0.305 → 0.778。
  三次重复的范围完全不重叠。
- **cot → structured 在 n=12×3 下分不出来**。separation 0.844 vs 0.856 落在
  彼此范围内。structured 的 kappa 和误报率更好（0.861 vs 0.778，0% vs 3%），
  方向一致但**不构成统计上的结论**。选 structured 是因为它额外产出可校验的
  引文——这是能力，不是本表证明的分数优势。
- **atomic 检出率最高（97%）但误报 14%，且 8–21% 的引文是编造的**。拆解出的
  原子断言里包含"为您推荐"这类礼貌措辞，上下文确实无法蕴含，严格聚合就把整个
  忠实答案judged 成不可信。**当前不作为默认模式。**

诚实的一句话结论：**幻觉检出率 30% → 86%，判官与真值的 Kappa 0.31 → 0.86**，
主要贡献来自要求裁判先说理由，其次来自强制取证。

## 5 判官与人工的一致性

### 5.1 为什么用 Kappa 而不是一致率

评估集永远是不平衡的——绝大多数答案是忠实的。一个"闭眼说忠实"的裁判在
85% 忠实的集合上一致率就有 85%，看起来很可信，实际毫无信息量。

Cohen's Kappa 扣掉了按观测基率瞎猜就能拿到的那部分：

```
kappa = (p_观测 - p_偶然) / (1 - p_偶然)
```

上面那个闭眼裁判的 kappa 是 **0**，一致率是 85%。这就是用它的全部理由。
（[`src/eval/alignment.py`](../src/eval/alignment.py) 里 `raw_agreement` 永远和
`majority_baseline` 并排打印——后者是前者必须超过才有意义的门槛。）

判官输出的是 0–5 的序数分而非一个 bit，所以同时算**二次加权 Kappa**：
按差值平方惩罚，"人 4 判 5" 和 "人 0 判 5" 不再等价，能看出"校准但偏松"和
"判反了"的区别。

### 5.2 抽检流程

```bash
# 1. 抽样。分层抽取，不是均匀 5%
uv run python -m src.eval.review_sample --out evaluation/review/latest.jsonl

# 2. 人工填 human_score（0.0–1.0）

# 3. 门禁
uv run python -m src.eval.alignment_gate --review evaluation/review/latest.jsonl
```

三个设计决定，每一个都对应一种会让 kappa 变得毫无意义的失败：

- **分层抽样**。不平衡集合里均匀抽 5% 几乎全是判官通过的用例，而一个只含两个
  失败样本的抽检说不出判官如何处理失败。按判官自己的通过/失败分层，两侧都有
  代表。低置信度用例无条件全部纳入。
- **判官分数写在另一个文件里**，评审看不到。先看到分数的评审会锚定在它上面，
  而一个认同了被递给他的数字的评审不是独立评分者——这样算出的 kappa 测的是
  暗示性，不是一致性。
- **门禁在样本缺失、为空、或过小时同样失败**。"没人评审过"绝不能和"评审员认同"
  报出同一个绿勾。少于 20 例时 kappa 的置信区间比门槛本身的余量还宽，此时报告
  它但拒绝据之放行。

门槛 **kappa ≥ 0.85**（Landis & Koch 的 "almost perfect" 区间下沿 0.81 之上留了
余量），每次发版抽检 5%。

## 6 已知局限

- 4.3 的 n 是 12 对 × 3 次重复。足以把 naive 和 cot 分开，**不足以把 cot 和
  structured 分开**，文中已按此表述。
- 构造真值是人工评审的**代用品**，不是替代品：构造用例比生产答案干净，所以
  4.3 的 kappa 是人工评审会给出的数字的上界。
- Batch API 只做打包与解析，提交流程留给调用方——OpenAI / Anthropic / DeepSeek
  的上传与轮询各不相同，用一个接口包住三家只会藏起真正会出问题的细节。
- 发版门禁需要仓库里有已评审的 `evaluation/review/latest.jsonl`。首次发版前
  必须先跑一次 `review_sample` 并人工填完，否则门禁会（正确地）失败。

## 7 断点续重试与死信队列 (Checkpointing & DLQ)

在海量 Batch 评测中，针对局部失败与网络中断引入了持久化管理机制（[`src/eval/dlq.py`](../src/eval/dlq.py)）：

1. **Checkpointing 断点恢复**：实时持久化 `TaskResult` 快照（`checkpoint.json`），任务重跑或异常恢复时自动跳过已完成项，重试等待时间降低 **>95%**，避免重复消费 Token。
2. **Dead Letter Queue (DLQ)**：捕捉失败任务收集至 `dlq.json`，支持 `retry_dlq` 精准重试，评测全集完成率达成 **100%**。
3. **更详细的设计与量化分析**：参见文档 [`docs/transactional_rollback_and_eval_dlq.md`](transactional_rollback_and_eval_dlq.md)。
